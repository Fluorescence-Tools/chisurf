# fdb Measurement and Data Analysis Database Scope

Status date: 2026-06-11

## Project Goal

`fdb` is the planned fluorescence database for chemical biology workflows in
ChiSurf. It should become a provenance-aware archive for fluorescence samples,
measurements, TTTR/raw data references, processing workflows, derived burst-wise and
analysis data products, model fits, parameter dependencies, and final archived
results.

The first implementation target is deliberately narrow: **Burst Selection plugin
processing of TTTR data**. This proves the database, processing, provenance, and
archive contracts before generalizing to ndxplorer, broader analysis workflows, and
later web/server use.

The long-term target is a backend that can be used from the ChiSurf desktop client,
headless JSON-RPC/ZMQ services, and eventually a web server without rewriting the
core data model.

## Core Principles

- Preserve provenance before adding broad UI: every result must be traceable back to
  raw files, processing settings, software versions, and sample/experiment context.
- Keep raw photon data external by default; store references, metadata, checksums,
  validation state, and small derived data where practical.
- Reuse existing ChiSurf services and plugin APIs instead of duplicating processing
  algorithms in the database layer.
- Keep current sample database and experiment-data behavior backward compatible.
- Extend the current SQLite schema incrementally with migrations and backup-before-
  migration behavior.
- Keep all service methods JSON-RPC-compatible so in-process dispatch, ZMQ, and a
  future web server can share one interface.
- Treat the first burst-wise TTTR slice as the reference workflow for later FCS,
  TCSPC, PDA, imaging, spectra, and model-fit provenance.

## Current Foundation

The current ChiSurf database work already provides enough infrastructure to start
`fdb` without a reset:

- Core database connector/plugin architecture for sample and experiment metadata.
- Source/user database separation and backup-before-migration behavior.
- SQLite migrations for samples, probes, positions, users, devices, experiment
  types, experiments, experiment data links, photon streams, analysis metadata, and
  small embedded analysis data.
- Repository methods for sample, user, device, experiment type, experiment,
  experiment data, metadata, spectra, optical properties, photon streams, and small
  embedded x/y analysis data.
- FLR CIF / mmCIF import and export paths for sample, experiment, and small analysis
  metadata.
- Sample Database GUI tabs for samples, conditions, entities, probes, label
  positions, metadata, users, devices, experiment types, experiments, and
  import/export.
- In-process RPC client wrapper for GUI-to-service calls.
- FitInfo support for metadata editing, external data references, lazy mmCIF export
  preview, and embedded small analysis curves.
- Burst Selection plugin architecture with API, CLI, GUI, server handlers, real-data
  tests, TTTR loading, photon filtering, burst summaries, GMM fitting, `.bur`, HDF5,
  ZIP, and JSON-compatible service results.

The missing piece is a normalized provenance layer that connects experiments, raw
TTTR files, burst-processing runs, derived products, analysis consumers, and archive
manifests.

## First Use-Case: Burst Selection TTTR Processing

The first vertical slice is the path from a measurement/experiment to archived
burst-wise products generated by the Burst Selection plugin:

```text
sample
  -> experiment / measurement
    -> raw TTTR/PTU/SPC/BH file reference
      -> burst_selection processing run
        -> .bur / HDF5 / ZIP / Info / .mti / summary products
          -> archive manifest and provenance graph
```

This first slice must not rework ndxplorer. ndxplorer is the next stop after burst
products are addressable through database records and service APIs.

### Raw TTTR records

Register raw photon files as first-class records linked to an experiment.

Required fields:

- raw data id
- experiment id
- file path, URL, or folder path
- file type: TTTR, PTU, SPC, BH, photon-HDF5, or other
- storage mode: local file, URL, folder, embedded small payload, or managed archive
- MIME/content type where known
- file size
- checksum and checksum algorithm
- TTTR header metadata as structured JSON
- detector/channel mapping
- acquisition software and version where available
- acquisition timestamps where available
- validation status and validation message
- created/updated timestamps

### Burst processing runs

Persist each Burst Selection job as a processing run. The database records the run;
the Burst Selection plugin remains responsible for executing the algorithm.

Required fields:

- processing id
- processing type: `burst_selection`
- linked experiment id
- input raw data ids
- serialized `AnalysisRequest` settings
- selected setup name
- detector definitions and PIE/window definitions
- operator/user id where available
- software package, module, and version
- runtime environment summary
- start/end timestamps
- status: pending, running, succeeded, failed, cancelled
- error message and traceback summary for failed runs
- aggregate counts: number of files, photons, selected photons, bursts

### Processed burst products

Register generated outputs as processed data records linked to the processing run.

Required product types:

- `.bur` burst tables
- HDF5 burst table exports
- ZIP archives
- legacy `Info/` folders
- `.mti` summaries
- generated feature tables
- GMM summaries from Burst Selection, when present
- JSON summaries and archive manifests

Required fields:

- processed data id
- processing id
- product type
- storage mode
- file path, URL, folder path, or embedded small JSON/table payload
- MIME/content type
- file size
- checksum and checksum algorithm
- row count or product-specific summary where available
- metadata JSON
- validation status

### Provenance edges

The first graph only needs the relationships required by burst-wise TTTR processing:

- experiment `has_raw_data` raw TTTR reference
- raw TTTR reference `input_to` burst processing run
- burst processing run `produced` processed burst product
- processed burst product `included_in` archive manifest

Each edge stores:

- source node type and id
- target node type and id
- relationship type
- processing id where applicable
- parameter/settings snapshot hash where applicable
- timestamp
- software version
- input/output checksum snapshot

## Phase Roadmap

### Phase 0 - Project framing and compatibility

- Rename the scope and project language from generic "sample database" expansion to
  `fdb`, the later fluorescence database for chemical biology.
- Keep existing sample database APIs and GUI names working during the transition.
- Document that database records are provenance metadata and not a replacement for
  raw TTTR storage.

### Phase 1 - Burst Selection TTTR provenance slice

- Add schema migration(s) for raw data references, processing runs, processed data
  products, and provenance edges needed by Burst Selection TTTR processing.
- Add repository methods for raw TTTR records, burst processing runs, processed
  products, and provenance edge queries.
- Add JSON-RPC service methods around the existing Burst Selection service shape:
  `raw_data.*`, `processing.burst_selection.*`, `processed_data.*`,
  `provenance.*`, and `archive.*`.
- Add a wrapper path that can run or record a Burst Selection job, persist its
  settings and result metadata, register generated `.bur`/HDF5/ZIP/Info/`.mti`
  outputs, compute checksums, and write provenance edges.
- Add archive manifest export for one burst-processing run.
- Keep ndxplorer out of this phase except as a documented consumer of registered
  burst products.

### Phase 2 - ndxplorer as the next consumer

- Load registered burst folders, HDF5 outputs, ZIP archives, and `.bur` products
  produced by Phase 1.
- Add ChiSurf JSON-RPC/ZMQ methods for headless ndxplorer operations only after
  Phase 1 products are database-addressable.
- Record ndxplorer selections, clustering/GMM results, plot/table exports, and
  analysis provenance as downstream records.
- Keep ndxplorer GUI behavior optional; service handlers should call stable reader,
  export, and analysis APIs rather than GUI window methods.

### Phase 3 - Setup definitions and generalized measurement records

- Add setup definition tables for instruments, optical paths, lasers, filters,
  detectors, detector/channel definitions, timing calibration, IRF definitions,
  burst defaults, FCS calibration, ALEX/MFD settings, TCSPC settings, and versioned
  setup history.
- Link measurements/experiments to setup definitions while preserving the existing
  experiment records.
- Add validation helpers for required setup fields used by TTTR and burst-wise
  workflows.

### Phase 4 - General processing and processed-data model

- Generalize the Phase 1 raw/process/product pattern to FCS correlations, burst
  histograms, microtime histograms, TCSPC decays, IRF curves, spectra, anisotropy
  curves, PDA histograms, RICS maps, fitted parameter tables, residual curves, and
  model curves.
- Add APIs for upstream/downstream dependency queries across raw and processed data.
- Preserve algorithm-specific settings as structured JSON until a normalized schema
  is justified by repeated use.

### Phase 5 - Analysis, model, fit, and parameter provenance

- Add analysis run records that consume processed data and produce model/fit results.
- Store model definitions, model versions, code/module versions, optimizer settings,
  convergence status, goodness-of-fit metrics, residuals, and fit summaries.
- Represent free, fixed, linked, shared/global, local, constrained, transformed, and
  expression-based parameter dependencies.
- Store fitted values, standard errors, confidence intervals, covariance information,
  and dataset-to-parameter mappings.

### Phase 6 - Archive and exchange formats

- Add JSON/JSONL provenance graph export.
- Extend mmCIF / FLR CIF export where the mapping is stable.
- Add SQLite backup archive export.
- Add ZIP/TAR archive export with manifest, checksums, database snapshot, exported
  JSON/mmCIF, and optional external data copies or references.
- Keep large raw TTTR/photon files external by default but make archive references
  reproducible through checksums and validation metadata.

### Phase 7 - GUI expansion

- Evolve the Sample Database window into a Measurement and Data Analysis Database
  window once the Phase 1 and Phase 2 service contracts are stable.
- Add focused views for raw data, burst processing runs, processed products,
  provenance, archive manifests, setup definitions, analyses, models, and parameter
  dependencies.
- Add "open in ndxplorer" actions for registered burst products after Phase 2.

### Phase 8 - Server and web readiness

- Ensure all service methods are JSON-RPC-compatible and callable through local
  in-process dispatch and ZMQ.
- Keep service interfaces stable enough for a later HTTP/websocket layer.
- Add audit logging for create/update/delete/archive actions.
- Add authentication and authorization hooks only when a remote multi-user server
  becomes an actual target.

### Phase 9 - Project Archive/Restore

- Add "to db" menu item under `File` in ChiSurf to archive the current project to the `fdb` database.
- Implement archiving of the entire analysis project state, including all ChiNet parameters, fit parameters, fit parameter widgets, and model types.
- Map the fit structure and interdependence of parameters introduced by the user during analysis.
- Ensure fits have UUIDs and are correctly linked across each other to preserve provenance.
- Add option in the database explorer to restore analysis projects directly from the database.
- Track how the analysis was created by saving the preprocessing steps from raw data to the final analysis project.


## Target Domain Model

### Sample

A sample record describes the biological or chemical specimen.

Required concepts:

- sample id and UUID
- name and description
- batch or preparation id
- buffer/composition, pH, temperature, solvent phase
- labeling strategy, probe positions, and probe stoichiometry
- preparation protocol
- operator, project, and related publications or internal records

### Setup definition

A setup definition captures measurement configuration independent of a single
measurement.

Required concepts:

- setup id, name, and version
- instrument/device
- optical path, lasers, excitation wavelengths, emission filters, dichroics
- detectors and detector/channel definitions
- timing calibration and TCSPC timing settings
- IRF definition
- FCS calibration
- burst selection defaults
- ALEX/MFD and polarization/anisotropy settings
- microscope objective and confocal volume metadata where relevant

### Measurement / experiment

A measurement links the sample, setup, operator, device, and raw data.

Required concepts:

- experiment id and experiment type
- sample id and setup definition id
- project id
- operator/user and device/instrument
- start/end time and status
- acquisition software/version and acquisition settings
- file links and checksums
- notes and key/value metadata

### Raw data

Raw data records are first-class references to measured data, not only free-text file
paths.

Required concepts:

- raw data id and experiment id
- data type: TTTR, PTU, BH/SPC, FCS raw, image stack, spectral raw, or other
- storage mode and location
- MIME/content type, size, checksum, and validation status
- acquisition metadata, timing metadata, detector/channel mapping, and calibration
  references

### Processing run

A processing run records a repeatable transformation.

Examples:

- raw TTTR -> burst selection
- raw TTTR -> microtime histogram
- raw TTTR -> FCS correlation
- raw image stack -> ROI traces
- raw spectra -> background-corrected spectra
- TCSPC raw -> IRF-corrected decay

Required concepts:

- processing id and processing type
- input data ids and output data ids
- algorithm name/version and code/module version
- parameter settings and calibration references
- operator, timestamp, runtime environment, and status
- failure details where applicable

### Processed data product

Processed data products are derived records.

Examples:

- burst lists and `.bur` files
- FCS curves
- burst histograms
- microtime histograms
- TCSPC decays and IRF curves
- spectra and anisotropy curves
- PDA histograms and RICS maps
- fitted parameter tables, residuals, and model curves

Required concepts:

- processed data id
- source raw/processed data ids
- processing id
- data type and storage mode
- embedded small arrays/tables where appropriate
- external file/folder/URL for large products
- units, metadata, checksum, and validation status

### Analysis run, model, and parameters

Analysis records capture the scientific interpretation of processed data.

Required concepts:

- analysis id and analysis type
- input processed data ids
- model id, model version, and code/module version
- fitting or optimization method and settings
- convergence status and goodness-of-fit metrics
- residuals, model curves, parameter tables, and notes
- parameter definitions, bounds, units, expressions, priors, initial values, fitted
  values, errors, confidence intervals, covariance, and global/local mappings

## Service Interface Targets

Phase 1 introduces the first stable public service groups:

- `raw_data.*`
- `processing.burst_selection.*`
- `processed_data.*`
- `provenance.*`
- `archive.*`

Later phases add:

- `setups.*`
- `analyses.*`
- `models.*`
- `fits.*`
- `parameters.*`
- `ndxplorer.*`

Existing `sample_database.*` and Burst Selection methods remain backward compatible.
The database/archive services should call or wrap existing plugin APIs rather than
move algorithmic code into the database package.

## Test and Acceptance Plan

### Phase 1 tests

- Migration test: a v12 database upgrades without losing existing sample,
  experiment, experiment-data, photon-stream, analysis-metadata, or analysis-data
  rows.
- Raw data test: a TTTR/PTU/SPC/BH path can be registered with size, checksum, file
  type, header metadata, detector/channel metadata, validation status, and
  experiment link.
- Burst processing test: a Burst Selection job can be run or simulated and persisted
  with serialized settings, status, counts, output paths, and failure details.
- Product registration test: generated `.bur`, HDF5, ZIP, `Info/`, `.mti`, and JSON
  summary outputs are registered with checksums and linked to the processing run.
- Provenance test: one experiment can be traced through raw TTTR input, burst
  processing run, processed burst products, and archive manifest.
- Archive test: exporting a burst-wise manifest includes raw file checksums,
  processing settings, output checksums, software version, and provenance edges.

### Later tests

- ndxplorer service tests load registered burst products and record downstream
  selections/analysis results.
- Setup-definition tests validate instrument and channel metadata required for TTTR
  and burst-wise workflows.
- Analysis/model tests verify parameter dependency graphs and fit-result exports.
- ZMQ integration tests prove the same service methods work through remote transport.
- Export tests verify JSON, SQLite, ZIP/TAR, and mmCIF/FLR CIF outputs where
  mappings are implemented.

## Non-Goals for the First Increment

- Do not rework ndxplorer in Phase 1.
- Do not add a standalone ndxplorer ZMQ server before burst products are
  database-addressable.
- Do not embed large raw photon streams in SQLite.
- Do not replace chinet.
- Do not normalize every processing algorithm or file format immediately.
- Do not block Burst Selection provenance on complete PDBx/PDB-IHM/mmCIF mapping.
- Do not remove existing sample database functionality.

## Success Criteria

Phase 1 is successful when ChiSurf can:

- register a raw TTTR/PTU/SPC/BH file under an experiment
- run or record a Burst Selection processing job
- persist the exact settings and software/runtime context for that job
- register generated burst-wise outputs with checksums
- answer which raw file and settings produced a given `.bur`/HDF5/ZIP output
- export a manifest that can reproduce the burst-wise provenance chain
- keep existing sample database and experiment-data behavior working

The broader `fdb` project is successful when the same provenance model
extends from burst-wise TTTR processing to ndxplorer, setup definitions, general
processing, analysis/fitting, parameter dependencies, archives, ZMQ services, and a
future fluorescence archiving web server.
