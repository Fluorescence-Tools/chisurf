# Summary
Introduces a deliberate SQLAlchemy mapping boundary for a bounded slice of MFDB
(sample, probe, FRET pair, vocabulary, and dictionary metadata tables) so
relationship-heavy features are expressed once and reused by the existing
repository API, without rewriting MFDB wholesale. It also corrects a schema bug
where FRET-pair (Förster radius) rows were globally scoped by probe IDs, causing
cross-sample leaks; the mapping makes the sample-scoped model harder to bypass.
`schema.py` stays the canonical migration source; SQLAlchemy models sit behind a
small adapter so GUI/plugin code never opens sessions directly.

# Status
Done. Foundational layer that must exist before dictionary-validation and
sample-tracking work is wired into a single persistence path.

# Goal
Introduce a deliberate SQLAlchemy mapping boundary for MFDB so
relationship-heavy features are expressed once, tested once, and reused by the
existing repository API. This PRD does **not** replace MFDB wholesale — it
creates a bounded SQLAlchemy slice for the tables that PRD-02a and PRD-02 depend
on most: sample, probe, FRET pair, vocabulary, and dictionary metadata tables.
The immediate driver is the R14 finding that raw SQL let FRET-pair data be
globally scoped by probe IDs, causing cross-sample leaks and uniqueness failures;
SQLAlchemy does not fix that schema bug by itself, but a mapped relationship
layer makes the correct sample-scoped model harder to bypass.

# Non-goals
- Do not rewrite all of `MFDatabase` in one pass.
- Do not introduce a second, competing schema definition.
- Do not mix ad hoc SQLAlchemy sessions into GUI/plugin code.
- Do not change the public MFDB API unless a method is already broken.
- Do not migrate object-store blob logic in this PRD.

# Design constraints
`schema.py` remains the canonical migration source during this phase. Existing
callers keep using `MFDatabase` and high-level modules like `sample_manager.py`.
SQLAlchemy models live behind a small internal adapter; callers never create
sessions directly. All SQLAlchemy transactions share the same sqlite database
path and must not race the existing `sqlite3` connection within one logical
operation. No mapping may hide a missing schema field — if a relationship needs a
foreign key or association table, add the schema change explicitly.

# Package layout
```text
modules/mfdb/src/mfdb/orm/
  __init__.py
  base.py              # DeclarativeBase, engine/session helpers
  models.py            # mapped classes for bounded MFDB slice
  sample_repository.py # SQLAlchemy-backed sample/probe operations
  sync.py              # schema/mapping consistency assertions
```

# Tables in scope
**Phase A — sample/probe core:** `mfdb_sample`, `flr_sample`,
`flr_sample_condition`, `flr_sample_probe`, `flr_poly_probe_position`,
`entities`, `entity_poly_seq`, `probes`, `chem_descriptors`,
`ihm_chemical_component_descriptor`, `optical_properties`, `spectra`,
`flr_fret_forster_radius`.
**Phase B — vocabulary/dictionary support:** `mfdb_vocabulary`, plus new
dictionary cache tables only if PRD-02a chooses a database-backed cache.

# Required schema correction before mapping
`flr_fret_forster_radius` must become sample-scoped. Minimal:

```sql
ALTER TABLE flr_fret_forster_radius ADD COLUMN sample_id TEXT REFERENCES flr_sample(sample_id);
CREATE UNIQUE INDEX IF NOT EXISTS idx_flr_forster_sample_pair
  ON flr_fret_forster_radius(sample_id, donor_probe_id, acceptor_probe_id)
  WHERE deleted_at IS NULL;
```

Preferred flrCIF-aligned form additionally links to specific
`flr_sample_probe.sample_probe_id` rows (`donor_sample_probe_id`,
`acceptor_sample_probe_id`) with a corresponding unique index. Use the preferred
schema unless compatibility with seeded data makes it too expensive.

# Tasks
1. **Add SQLAlchemy as an explicit dependency** (bounded version) so
   `import sqlalchemy` works in the arm64 dev environment; no GUI/plugin imports
   SQLAlchemy directly.
2. **ORM base and session adapter** (`orm/base.py`): `make_engine(db_path)`,
   `session_scope(db_path)` (commit/rollback), `session_from_mfdatabase(db)`. If
   binding safely to a live `MFDatabase` isn't possible, document that
   SQLAlchemy-backed methods open short-lived by-path sessions and must not run
   inside active `db._transaction()` blocks.
3. **Map the bounded model** (`orm/models.py`): `MfdbSampleIndex`, `FlrSample`,
   `FlrSampleCondition`, `FlrSampleProbe`, `FlrPolyProbePosition`, `Entity`,
   `EntityPolySeq`, `Probe`, `OpticalProperty`, `Spectrum`,
   `FlrFretForsterRadius`, with relationships (`FlrSample → sample_probes →
   Probe`, `FlrSampleProbe → poly_probe_position → Entity`, `FlrSample →
   condition`, `FlrSample → fret_pairs`). `FlrFretForsterRadius` is scoped to one
   sample. Model metadata is comparable against the live sqlite schema without
   creating/mutating tables.
4. **SQLAlchemy-backed sample repository** (`orm/sample_repository.py`):
   `create_sample_graph(db, definition) -> str`, `get_sample_graph(db,
   sample_id) -> dict | None`, `upsert_probe(db, probe) -> int`. Initially
   test-only; once verified, `create_sample()`/`get_sample_full_description()`
   delegate to it.
5. **Preserve public API** — refactor `create_sample()`,
   `get_sample_full_description()`, `validate_sample_for_export()` to call the
   adapter without changing signatures; keep the lightweight `mfdb_sample` index
   intact.
6. **Schema/mapping consistency checks** — tests that fail when mapped columns
   drift from `schema.py`: every mapped column exists live; every required
   relationship has a FK or explicit join; `flr_fret_forster_radius` has sample
   scope; no model calls `Base.metadata.create_all()` against production DBs.
7. **Regression tests for R14** — two samples with the same donor/acceptor dye
   names but different R₀ can both be created; a sample sharing one probe with
   another does not return the other's FRET pair; probe chemical fields persist
   to canonical probe/descriptor tables; request-layer custom probe names warn
   instead of raising.

# Definition of Done
- SQLAlchemy dependency declared and importable.
- ORM mapping exists for the bounded MFDB sample/probe slice.
- Existing public sample APIs still work.
- R14-1 (sample-scoped FRET pairs) and R14-4 (probe chemical fields persisted to
  canonical tables) fixed by schema/API behavior, not only by metadata JSON.
- Focused sample tests pass without relying on global probe-pair uniqueness.
- PRD-02a can build dictionary validation on a stable MFDB relationship boundary.

# Risks
- **Dual transaction model** — sqlite3 and SQLAlchemy sessions can conflict if
  mixed in one operation; route sample-graph operations through one adapter and
  document transaction boundaries.
- **Schema drift** — mappings can become a second schema source; mitigate with
  consistency tests and by keeping `schema.py` canonical for migrations.
- **Scope creep** — keep this PRD limited to the sample/probe/FRET/vocabulary
  surfaces needed before PRD-02a and PRD-02.

As built, the ORM adapter routes public sample create/read through the bounded
mapping; the focused MFDB suite passes (114/114 with a writable HOME), and R14-1
FRET-pair scoping and R14-4 probe-field persistence are resolved at the schema/
API level.
